# Techely Learning Academy — Full Project Analysis Report

**Date:** 2026-08-16  
**Project:** Coaching Center Management System (Admin Panel + Student Portal + Public Website)

---

## 1. Executive Summary

This is a full-stack React web application for **Techely Learning Academy** — a coaching center management system. It has three distinct surfaces:

- **Public website** — landing page, courses, admission form, notices, contact
- **Admin panel** — manage students, batches, teachers, fees, exams, notices, SMS, reports, settings, backups
- **Student portal** — login, dashboard, fees, exams, results, notices, profile

The architecture is clean and well-structured. The UI is modern with Bengali/English support, animations, charts, and responsive design. However, it **is NOT production-ready** in its current state — there are several critical blockers including missing tests, no CI/CD, unhandled errors, and security gaps.

**Verdict: Great foundation, needs work before going live.**

## 3. Architecture & How It Works

### 3.1 Authentication

**Two separate auth systems:**

1. **Admin** — Uses Supabase Auth (`useAuthStore`). Admins log in at `/admin/login`. The `role` field is stored in `user_metadata.role`. Protected by `ProtectedRoute` which checks `role === 'admin'`.

2. **Students** — Custom phone + password auth against the `students` table (`useStudentStore`). The password is stored as plaintext in the database. Session is stored in `sessionStorage` via Zustand's `persist` middleware. Protected by `StudentProtectedRoute`.

### 3.2 Database

Single Supabase PostgreSQL database. The `migration.sql` file adds missing columns to pre-existing tables and creates new tables:

- **Extended tables:** `students`, `teachers`, `batches`, `fees`, `exams`, `notices`, `admission_requests`
- **New tables:** `mcq_questions`, `mcq_submissions`, `site_settings`, `fee_audit_logs`

Row Level Security (RLS) is enabled on `mcq_questions`, `mcq_submissions`, and `site_settings` with public read + authenticated full access policies.

### 3.3 State Management

- **Zustand** stores for auth, student session, and settings
- Settings are persisted to `localStorage` and synced with the `site_settings` DB table
- 27 configurable settings mapped between UI fields and DB keys

### 3.4 Routing

- Lazy-loaded admin and portal pages for code splitting
- Public pages eagerly loaded (small, needed on any direct URL)
- Auth pages eagerly loaded (needed before lazy chunks resolve)
- Custom 404 page

### 3.5 PDF Generation

- Receipts and result cards are generated by opening a popup window with styled HTML and triggering `window.print()`
- Uses Google Fonts (Noto Sans Bengali, Inter)
- XSS prevention via `escapeHtml`

### 3.6 SMS Notifications

- 6 Bengali SMS templates (fee reminder, fee paid, exam notice, result out, general notice, approved)
- Regex-based template variable substitution
- Logs to `sms_logs` table
- Falls back to 'pending' status if no API key

## 6. Detailed Issues & Points for Improvement

### 6.1 Security Issues

1. **Plaintext Student Passwords** (`src/store/useStudentStore.ts`, `migration.sql`)
   - `students.password` is stored as raw TEXT
   - Fix: Hash with bcrypt, add migration, update login flow

2. **Overly Permissive RLS** (`migration.sql`)
   - `mcq_questions` and `mcq_submissions` allow public SELECT
   - Anyone can see all exam questions and all student scores
   - Fix: Restrict to authenticated users or add exam-date-based logic

3. **No Input Sanitization**
   - Student names, notice content, batch descriptions rendered without sanitization
   - Fix: Add DOMPurify for rich text, escape all user inputs

4. **No Rate Limiting**
   - Student login has no throttling
   - Fix: Add Supabase Auth rate limits or implement custom throttling

### 6.2 Code Quality Issues

1. **Module-Level Auth Subscription** (`src/store/useAuthStore.ts`)
   ```typescript
   // This is at module level, not inside the store
   let authSubscription: any = null;
   ```
   - Risk: If store is re-initialized, old listener may persist
   - Fix: Move subscription management inside the store lifecycle

2. **Missing Error Boundaries**
   - `ErrorBoundary` only wraps the root — lazy-loaded pages have no fallback
   - Fix: Add error boundaries per section or per route

3. **Inconsistent Error Handling**
   - Some Supabase calls check `error`, others don't
   - Some show toasts, others silently fail
   - Fix: Standardize with a `handleSupabaseError` utility

4. **TypeScript `any` Usage**
   - Multiple places use `any` type (e.g., `data: any`, `as any`)
   - Fix: Define proper interfaces for all responses

5. **Magic Numbers**
   - `PAGE_SIZE = 20` scattered in StudentsPage
   - Fix: Extract to constants file

### 6.3 Architecture Issues

1. **Two Auth Systems**
   - Admin uses Supabase Auth, students use custom auth
   - Creates maintenance burden and security inconsistency
   - Consider: Unify under Supabase Auth with custom claims

2. **Settings Key Mapping Complexity** (`src/store/useSettingsStore.ts`)
   - 27 fields mapped between UI and DB with manual key mapping
   - Error-prone when adding new settings
   - Consider: Convention over configuration, or a schema-driven approach

3. **No API Layer**
   - Components call `supabase` directly
   - No abstraction for data fetching, caching, or error handling
   - Consider: Add a data layer with TanStack Query

### 6.4 Performance Issues

1. **No Memoization Strategy**
   - Dashboard fetches 5+ queries in parallel every render
   - Students page re-fetches on every filter change
   - Fix: Add React Query with caching and stale-while-revalidate

2. **Large Bundle Risk**
   - Admin pages are lazy-loaded (good), but no bundle analysis
   - Fix: Add bundle analyzer to identify large dependencies

3. **No Image Optimization**
   - Photos loaded as full URLs without sizing
   - Fix: Use Supabase image transformation or lazy loading

### 6.5 UX Issues

1. **PDF Popup Dependency**
   - `window.open()` for receipts/result cards
   - Modern browsers block popups by default
   - Fix: Use inline print or Blob download

2. **No Offline Support**
   - PWA capabilities not implemented
   - Consider: Service worker for offline exam access

3. **No Accessibility Labels**
   - Icon-only buttons lack `aria-label`
   - Form inputs lack explicit `aria-describedby`
   - Fix: Add accessibility attributes

## 8. Deployment Configuration

The project has deployment configs for two platforms:

### Vercel (`vercel.json`)
- Build: `pnpm install && pnpm run build`
- Output: `dist/public`
- SPA rewrite configured
- Environment: PORT=3000, BASE_PATH=/

### Netlify (`netlify.toml`)
- Base: `artifacts/coaching-center`
- Build: `pnpm install && pnpm run build`
- Publish: `dist/public`
- SPA redirect with 200 status

**Issue:** The Vite config requires `PORT` and `BASE_PATH` environment variables and throws if missing. This works in Vercel/Netlify but would break in a generic Docker setup.

2. **Add tests** — Start with critical paths: auth, fee payment, exam submission
3. **Add error handling** — Wrap all Supabase calls with try-catch
4. **Fix RLS policies** — Restrict public access to exam data
5. **Add input sanitization** — Install DOMPurify, sanitize all user inputs

### Short-term (First 2 Weeks)

6. **Set up CI/CD** — GitHub Actions for test + build on PR
7. **Add error tracking** — Sentry or similar
8. **Implement rate limiting** — On student login endpoint
9. **Add loading states** — Skeleton screens for all data tables
10. **Fix PDF popup** — Use inline print approach

### Medium-term (First Month)

11. **Unify auth** — Consider moving students to Supabase Auth
12. **Add React Query** — For data fetching, caching, and optimistic updates
13. **Add bundle analysis** — Identify optimization opportunities
14. **Implement automated backups** — Supabase has point-in-time recovery, verify it's configured
15. **Add health checks** — `/health` endpoint for monitoring

### Long-term (Ongoing)

16. **PWA support** — Service worker for offline capability

## 12. Final Verdict

**This is a solid, well-architected application** with a modern tech stack and thoughtful UX. The code is clean and the feature set is comprehensive. However, it has **critical security gaps** (plaintext passwords, permissive RLS) and **zero testing infrastructure**.

**To make it production-ready:** Focus on the CRITICAL and HIGH blockers first — especially password hashing, tests, and error handling. After those are addressed, the app will be in good shape for a controlled launch with monitoring in place.

**Estimated time to production-ready:** 4-5 weeks of focused engineering work.
